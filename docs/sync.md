# Etude Sync

Sync keeps a local collection on every device. Work offline, then exchange encrypted events through a shared folder or etude-cloud. The CLI reference lists the `sync` commands. Settings → Sync uses the same core and API in Node and the browser worker.

## Local log and identities

Setup installs SQLite triggers in the collection. Triggers capture inserts, updates and deletes inside the engine transaction, and advance a persisted hybrid logical clock using the SQLite wall clock, a counter and a random device id. A clock rollback increments the counter. Receiving a remote event advances the clock before the next edit. Rolled-back writes leave no events. Sync drains raw changes into field registers and an append-only event log.

Decks, attempts and reviews have stable random identities alongside their local integer handles. Cards receive an identity from their initial item and face, which stays stable when a face is renamed. Item ids, preset ids, type ids and scheduler ids remain their existing stable ids. Integer handles remain local and are translated at the boundary.

Registers compare wall time, logical counter and device id. JSON object leaves merge independently; arrays merge as one field. Item tag membership merges per tag. Entity deletes create permanent tombstones. Reusing a deleted identity is unsupported; use a fresh identity for new content. Two independently created decks with the same name remain separate; the later sorted identity receives a short suffix in the relational view.

Every change that moves a register, received or drained from this device, records its key in `sync_dirty` in the same transaction, with the scheduling fields it touched (a deck's name, preset or config, an item's deck, type or creation date, a type's scheduler, the day start). The projection then rewrites only those keys and the rows that depend on them: the items of a deck or type that appears or goes, the cards of such an item, the history of such a card, and attempts and reviews that name each other. Deck names are recomputed together, since a duplicate's suffix depends on the others. It runs in one transaction with capture muted, and foreign keys are deferred to its commit. Titles, search text and item_tags are rebuilt for the items it wrote. A crash leaves the keys for the next sync. The full rebuild stays as the reference: it runs on the first sync of a collection with this version, when shipped type or scheduler definitions change, and when an incremental pass fails (the error is kept in `sync_meta` as `fallback`). No remote event is emitted again. Each pulled page is decrypted first and then applied with its cursor in one transaction. The folder transport lists the per-device event files on each sync and reads only those whose event this device doesn't have, so a file that arrives late, after newer ones, is still found. Cloud transport persists the server cursor after durable receipt, pushes in batches and retries the same event id and ciphertext.

## Scope

Synced content: presets; deck names, descriptions, instructions, archive state, order and configuration; items and their individual JSON fields, tags, source, notes, dates, order and archive state; customized card types and schedulers; type folders and placements; tag metadata; attempts and graded answers; reviews; card suspension, burial and explicit reset/due controls; media and type assets. Shipped defaults are supplied by the app; custom edits and resets of edited definitions are logged.

Synced settings are dayStartHour, learnAheadMinutes, selected theme and custom themes. All AI configuration stays local, including provider URLs, model selection, language, env-key names and agent effort. Device-local content also includes ChatGPT credentials and host ids, API keys, update state, window/sidebar state, Market installation receipts, Ask Etude conversations, attachments and snapshots, server authentication options, Sync tokens, vault keys and cursors. The market catalog address remains local.

Reviews and attempts have independent identities, so simultaneous offline answers both survive. Removing an item hides its orphan history from the relational view; the event log retains it. Explicit review undo records a retraction tombstone. It takes the device's own most recent review: one that arrived from another device is never undone there, so two devices can't retract the same review. Snapshot-based Ask Etude undo is refused in synced collections because a whole-database restore would overwrite sync identity and causality. Ask Etude can inspect status and request sync; credential-entry commands remain outside its tool access.

## Scheduling

Each merge replays live reviews in timestamp order with stable review identity as a tie-break. Only cards whose history or configuration changed are replayed. Each card's canonical state after the last review it was replayed to is kept in `sync_replay` with that review's time and identity: when every changed review comes after it, the card continues from there; an earlier, removed or rewritten review, or a change to the card, its item or its deck, replays it from the first review. A deck, preset or type scheduler change replays the cards it configures, subdecks included; a scheduler or day-start change replays every card. FSRS replay keeps the deck's fuzz and evaluates deadline caps at each recorded review time. The fuzz is drawn from a seed made of the card's key (its sync key, or the `[item, face]` pair a sync key is made from) and the number of the review: no time and no floating point, so every device, every JavaScript engine and the rating buttons draw the same. An FSRS card therefore gets the same schedule from rating, from its rating buttons, from rescheduling and from the sync replay, and its date doesn't move at the next sync. Rescheduling in a synced collection also orders tied reviews by identity and starts a reset card from its reset. Two offline reviews of one card on different devices can carry the same review number; after the merge, the one later in replay order becomes the next review and its fuzz is drawn for that number, so its date can move by a day or two at that sync. A trigger still marks cards whose schedule this device changed, and the next sync replays them canonically. Drill, Leitner and user scripts replay with the canonical preceding history, including tied timestamps. Sync replay uses UTC study days and the synced day-start hour so machines in different time zones converge. Script Date.now(), argument-free new Date() and Math.random() are deterministic. The script receives the review's clock and a random stream seeded by the card's key and the review number. Reset controls preserve history and start a fresh scheduling state; due overrides remain until a later review.

A script that throws or exceeds the sandbox budget aborts the projection transaction and surfaces its error. Received events remain durable for retry after the script is repaired. There is no fallback to a guessed scheduling state. Historical scheduling changes and resets made before the first setup have no separate event timeline; first merge replays the available review history using the current merged scheduler and configuration.

## Encryption and secrets

The client implements etude-cloud's version-1 scheme: a random 256-bit vault key; Argon2id with 64 MiB, three passes and one lane for the Sync password; AES-256-GCM wraps; a checksummed 240-bit recovery key; HKDF-derived event, blob and snapshot subkeys. Event authentication binds the event id. Blobs are named by the SHA-256 of their ciphertext. A synced plaintext-hash → ciphertext-name map lets later devices reuse existing uploads. Plaintext hashes and filenames travel inside encrypted events.

Account sign-in uses email start → code → verify → revocable device token. With two-step sign-in on (Settings → Account), verify only returns a short-lived ticket, kept beside the token, and the authenticator code or a recovery code (`account second-factor`, `sync second-factor`) gets the token. Reading the key envelope requires that token. A vault is kept in one of two modes, reported as `mode` by `sync status`:

- **No password** (`server`), the default where the server can keep keys (`/v1/server` reports `sync.withoutPassword`): the first device sends the vault key to the server, which keeps it wrapped with a key only the server has. A device that signed in within the last 10 minutes gets it with no password. Events and blobs are still encrypted on the device and stored as ciphertext, but this isn't end-to-end: whoever runs the server, or takes over the email account, can read the collection.
- **Sync password** (`password`): end-to-end. Unlocking requires the Sync password or recovery key, and the server never has the vault key. A server that can't keep keys always uses this mode.

The first unlock creates the envelope with a conditional initial PUT; cloud envelope updates support If-Match through the transport. `sync protect` (Settings → Sync → Add a Sync password) wraps the open vault key with a new password and recovery key and drops the server's copy in the same write; `sync unprotect` hands the key back to the server and drops the password and recovery wraps. Neither re-encrypts existing events: the vault key stays the same, so anyone who could read it before still can. The UI shows the generated recovery key once and asks for an explicit saved-key confirmation. Passwords stay in memory for the request. Neither passwords nor recovery keys are saved. A shared folder always uses a Sync password.

Desktop tokens and the unwrapped vault key live in a collection-device-specific JSON file under `$ETUDE_HOME/sync/`, beside the existing credentials area, with directory mode 700 and file mode 600. The browser uses the worker's credential filesystem mirrored into OPFS. Both depend on the security of the local device and application origin. The local collection and caches contain plaintext. With a Sync password, an account takeover alone cannot open the cloud data; without one, it can. Malicious same-origin code, a compromised app build, local OS access or browser-profile access can obtain the saved key. Browser eviction can remove the local copy; the app requests persistent storage. Transport metadata still reveals sizes, event counts and timing.

## Running

A shared folder needs no account. Choose the folder on each desktop, create a Sync password on the first device and unlock the others. The directory contains keys.json, per-device encrypted event files and encrypted blobs. Sync software can copy those files between computers. Browser builds use cloud transport.

For cloud, configure the server URL, sign in by email, paste the code, then start Sync (with or without a Sync password) or unlock the vault. HTTPS is required outside localhost. Browser clients need their exact origin in the server's `ETUDE_CLOUD_ORIGINS`, including the port for local tests. Server CORS exposes ETag for the wrapped-key protocol. Quota and entitlement errors are shown using the server message.

A sync runs in two phases. The collection comes first, and `/api/sync/now` and `/api/sync/auto` return when it is done: on a device's first sync, the vault's snapshot when it has one (see Snapshots), then download (events from other devices, each page applied in one transaction), then the card types' assets (the types step: their blobs, which the projection reads, are downloaded when missing and this device's new ones uploaded, each before the events that name it are sent), upload (this device's events) and apply (write the changes into the relational view). A type asset whose blob event hasn't arrived is left out of the projection and its key stays marked for the sync that brings it; this device's own asset keeps its bytes until its upload. Media files follow in a background task: check (hash the local media), download (media blobs this device lacks) and upload (new files, then their media and blob events). So a review or a new deck from another device never waits for media files, this device's changes go up before its files do, and a new device shows the collection before its first file arrives. The CLI's `sync now` is a process that ends: it waits for the media too and exits with the media's error if it failed.

`sync status` reports the collection as `busy`, `error` and `progress`, and the media as `media`: `active` while the task runs, its own `progress` and `error`, and `received`, the files from other devices written since the process started. `progress` gives the step, bytes done, the total when known and the transfer rate; the check step counts files. Settings → Sync says what each step moves (your collection, changes from your other devices, card types, your changes, your cards, media files) with a verb that takes turns every few seconds, the plain one first. The snapshot and upload totals are exact. The download total is the server's vault size on a device's first sync and unknown afterwards. A media failure doesn't fail the sync: the collection is in step, the error shows only under `media` (an automatic sync keeps network errors quiet, as it does for the collection), and the next sync looks at every file again.

One media task runs at a time. A sync that starts during it syncs the collection as usual and doesn't start another; when media or blob events came in, the running task makes one more pass when it ends. Turning Sync off, setting it up, unlocking and closing the collection stop the task between files and wait for it; what it wrote and sent so far stays consistent, and the next sync goes on from there. Pushes take turns, so the collection and the media task never send the same events at once. A downloaded file is written under a `.etude-partial-` name beside its place and then renamed, so a write cut short (the app closed) never leaves half a file under the real name, where it would look like this device's edit or, under `files/`, be trusted by its name. The check step skips such files and removes them once they are ten minutes old.

Events come down in pages of up to 1,000 (the server also stops a page at 8 MiB). Blob downloads and uploads run sixteen at a time, which stays under etude-cloud's 100 requests a second per device; when the server answers 429 Too Many Requests, the request waits for its Retry-After (at most 60 s, with jitter) and tries again, up to 30 times, and each downloaded media file is written as soon as its blob arrives. Each device records the version of every media file it last had in step with the registers (`sync_media_seen`): a local file that still matches it takes a newer version from another device, and one that doesn't is uploaded as this device's edit. Media paths are refused only for control characters, backslashes, empty, `.` or `..` segments, or resolving outside the media folder, and such entries are skipped. The media task skips the files when no media event came in or waits and no media folder had a file added, removed or renamed since it was last read. A folder's time doesn't change when a file in it is rewritten in place, so every file is also looked at on the first sync of a process and at least every ten minutes; that's when such an edit is found. Files Etude stored are named by their SHA-256 and aren't read to hash them, unless the name matches neither the registers nor the version last in step with them. Media bytes stay on disk; only type assets keep theirs in `sync_blobs`, for the projection. A media file whose blob event hasn't arrived yet waits for a later sync.

The app reads the status on opening and after each automatic sync, and while media comes in every two seconds, also during a study session. Until then a collection image that isn't on this device yet shows a dashed "Image on its way" card instead of a broken image, in a card and on the app's pages. When files arrive, the app tells open cards and images, and a card asks again for the collection's images and sounds that failed to load (in the browser build and the phone apps, the frame asks the app for them again). Once no media is on its way, a file still missing shows as missing. A missing `/media` file is answered with `Cache-Control: no-store`, also under `files/`, which is otherwise cached for a year. Settings → Sync shows the media's progress under the collection's, saying the collection is already up to date.

The open UI syncs on startup, after a review session ends or is left, and every three minutes outside the active study view. Network failures during automatic sync stay quiet. Manual sync shows failures. Sync stays optional and local study continues offline. The projection holds the thread while it runs, but its cost follows the number of changes; only the one-time full rebuild is proportional to the collection.

## Snapshots

A new device doesn't replay the whole log when the vault has a snapshot: the merged registers and tombstones up to a server seq, written by a desktop device and kept on etude-cloud (`GET`/`PUT /v1/vault/snapshot`). The device merges the snapshot, moves its clock past every stamp in it, sets its cursor to the snapshot's seq, pulls only the events after it and runs the full projection once. The registers are a state-based CRDT, so this ends exactly where replaying the log ends: merging keeps the newest stamp of every field and tombstone, as `apply` does, and an event the snapshot already includes changes nothing when it comes again. The events stay on the server, so an app without snapshots still syncs from the whole log.

A snapshot is stored in parts of 50,000 registers (about 8 MB of JSON for a typical collection), so a phone holds one part at a time. Each part is gzip-compressed JSON, `{v:1, part, last, registers:[[tbl,key,field,value,stamp],…], deleted:[[tbl,key,stamp],…]}` with the tombstones in the first part, encrypted with AES-256-GCM under the snapshots subkey (HKDF info `etude-snapshots-v1`) and uploaded as a blob named by the SHA-256 of its ciphertext. The AAD is `etude-snapshot:v1:<id>:<seq>:<part>`, so the server can't reorder parts, mix two snapshots or claim a later seq, and the last part says it is the last, so parts dropped from the end are noticed. A part is merged with its progress in one transaction, so a sync cut off in the middle goes on from the next part, and the next part downloads while one merges. A snapshot that can't be read (a part changed, missing or out of place, a table this app doesn't know) is set aside with its error in `sync_meta` as `snapshot_error`, and the device syncs from the whole log, which gives the same registers; one replaced while its parts downloaded is read again once.

Only the desktop and the CLI write snapshots: after a sync, once the log has grown by 20,000 events since the vault's last snapshot (`ETUDE_SYNC_SNAPSHOT_EVERY` changes it), and only with nothing waiting to be sent, after the media task. The registers are read in one go, so they hold exactly the events up to the cursor and this device's own, which are on the server too. The parts go up first, then the pointer, with If-Match: a device that loses the race to another one's snapshot deletes its parts, and parts an attempt uploaded without getting to the pointer are deleted on the next attempt. The server deletes the previous snapshot's parts when the pointer moves. A server without snapshots answers 404, and the device asks again a day later. Once a day it also asks when the log hasn't grown enough, for what it can't see on its own: a server that gained snapshots, or a snapshot gone with a vault reset.

## Verification

`npm test` and `npm run test:wasm` each run the seeded folder property test. It simulates three collections, 240 random offline operations, FSRS/drill/Leitner/a custom seeded scheduler that reads its history, reviews with fuzz, reviews on cards later deleted, undo after a sync, graded attempts, decks created twice offline, renamed and merged, deck config, presets, a type's own scheduler, the day start, suspension, reset and due controls, tombstones, field merges, media, assets and shuffled sync interleavings. After every sync of every device it compares the relational view with a full rebuild of a copy of the same registers, by stable identities (sync ids, item ids, card keys): card schedules, review states, item titles, search text and tags, deck names with suffixes, settings and type assets. Another test delivers an attempt before its review and a review before an earlier one. `ETUDE_SYNC_SEED` (decimal or `0x` hex) runs the property test with another random stream. `test/fuzz.test.ts` checks that rating, the rating buttons, rescheduling and the sync replay give a card the same schedule, on one device and two, that fuzz spreads cards answered alike, and that the fuzz seed has no time or floating point in it. A second property test uses a real cloud instance when ETUDE_SYNC_TEST_SERVER and ETUDE_SYNC_TEST_OUTBOX point to an isolated file-mail server. It uses synthetic example.test accounts. Run it with `ETUDE_SYNC_SNAPSHOT_EVERY` low (and `ETUDE_SYNC_SNAPSHOT_PART` small) and the devices make and replace snapshots along the way; at the end a fourth device joins from the latest one, pulls only the events after it and must match the others and a full rebuild. `test/sync-snapshot.test.ts` covers the rest against a small fake server: a new device against one that replays the whole log (the same registers), parts out of order, from another snapshot, with a later seq claimed or the last one dropped, a sync cut off between parts, a lost race and an older server. Run both suites to exercise both SQLite drivers.

The integration test credentials and servers must be disposable. Never point these variables at an account that sends real email. The report for this implementation records the real collection-copy/Chromium acceptance run and screenshot paths.
